## 2. Why a code-only change is impossible

The consent screen shows **whatever host is in `authDomain`**, because that host
must serve the OAuth callback at `/__/auth/handler`.

That path is **generated by Firebase Hosting**. It is not a file that can be
committed — GitHub Pages has no way to produce it. Confirmed above: the apex
domain returns 404 for that path.

So `authDomain` can only be changed to a host that Firebase Hosting serves.
Google's own documentation states this directly:

> "If you host your app with Firebase Hosting using a custom domain, you can
> configure the Firebase SDK to use your custom domain as the `authDomain`.
> (If you don't use Firebase Hosting, you need to use a different option.)"
> — [Firebase: redirect best practices](https://firebase.google.com/docs/auth/web/redirect-best-practices)

> "From the Firebase console, connect your project to a custom domain … In your
> app configuration, update the callback URL with your custom domain … change
> `https://myproject.firebaseapp.com/__/auth/handler` to
> `https://auth.mycustomdomain.com/__/auth/handler`."
> — [Identity Platform: showing a custom domain](https://cloud.google.com/identity-platform/docs/show-custom-domain)

**Important:** setting a nice "App name" in the OAuth consent screen does *not*
replace the domain line. Google shows the app name only for apps that have gone
through verification; for an unverified app it falls back to the redirect host.
That is why the project id is showing.

---

## 3. The chosen approach — and why it is the safe one

Use a **dedicated subdomain**: `auth.rabbihossainltd.online`.

The apex and `www` stay exactly where they are, on GitHub Pages. Nothing about
the current site moves. We only add one brand-new DNS record for a hostname that
is currently unused, so there is no way to break the live site while setting up.

Rejected alternatives:

- **Point the apex at Firebase Hosting** — would move the whole website off
  GitHub Pages. Far too risky for a cosmetic change.
- **Leave it and just rename the app** — does not work (see above).
- **Proxy `/__/auth/**` from GitHub Pages** — GitHub Pages cannot proxy or
  rewrite. Not possible.

## 4. Console steps (must be done by you — these are not code)

Do them **in this order**. The site keeps working throughout; nothing changes
for users until the very last step.

### Step 1 — Firebase Hosting: add the auth subdomain

Firebase Console → **Hosting** → *Add custom domain*

- Domain: `auth.rabbihossainltd.online`
- **Do not** tick "Redirect to an existing site"
- Firebase gives you DNS records to add

### Step 2 — Hostinger: add the DNS records

Hostinger → DNS zone for `rabbihossainltd.online`

Add **only** the records Firebase shows you, on the `auth` host:

```
Type: TXT   Host: auth   Value: <verification string Firebase gives>
Type: A     Host: auth   Value: <IP Firebase gives>   (usually two A records)
```

⚠️ Only touch the `auth` host. Leave the apex `A` records
(`185.199.108–111.153`) and the `www` CNAME alone — those are the live site.

Wait for Firebase to show **Connected** and issue the certificate
(usually 15 minutes to a few hours).

### Step 3 — Firebase Auth: authorise the domain

Firebase Console → **Authentication** → **Settings** → *Authorized domains*
→ **Add domain** → `auth.rabbihossainltd.online`

Keep every existing entry — especially `rabbihossainltd.online`,
`rabbihossainltd-63709.firebaseapp.com` and `localhost`.

### Step 4 — Google Cloud: update the OAuth client

Google Cloud Console → **APIs & Services** → **Credentials** →
OAuth 2.0 Client IDs → the one ending
`…-gvdc7r91vmv6sfq8vtd9a3n2caubljcn`

**Authorized JavaScript origins** — add (keep existing):
```
https://auth.rabbihossainltd.online
```

**Authorized redirect URIs** — add (keep existing):
```
https://auth.rabbihossainltd.online/__/auth/handler
```

⚠️ **Do not remove** `https://rabbihossainltd-63709.firebaseapp.com/__/auth/handler`.
Keeping both is what makes the switch reversible — if anything goes wrong you
can flip the flag back and sign-in keeps working.

### Step 5 — Branding

Google Cloud Console → **Google Auth Platform** → **Branding**

- App name: `Rabbihossainltd`
- User support email: `rabbihossainltd@gmail.com`
- Application home page: `https://rabbihossainltd.online/`
- Privacy policy: `https://rabbihossainltd.online/privacy-policy/`
- Terms of service: `https://rabbihossainltd.online/terms/`
- Authorized domains: `rabbihossainltd.online` (the root covers the subdomain)

### Step 6 — Verify the handler responds

Before touching any code, check:

```
https://auth.rabbihossainltd.online/__/auth/handler
```

It must return **200**, not 404 and not a certificate warning.
**If it does not, stop.** Flipping the flag now would break sign-in.

### Step 7 — Flip the switch (one line)

In `js/firebase-config.js`:

```js
export const USE_CUSTOM_AUTH_DOMAIN = true;
```

Commit, push, wait for Pages to deploy, then hard-reload (the service worker
caches config; the cache version was bumped for this change).

The consent screen should now read:

> Sign in to continue to **rabbihossainltd.online**

### Rollback

Set the flag back to `false` and push. Because step 4 kept the original
redirect URI, sign-in returns to the working default immediately.

## 5. What was changed in code

The Firebase config was duplicated in **six** places — `js/auth.js`,
`js/firebase-core.js` and four inline `<script type="module">` blocks in
`index.html`, `about/`, `portfolio/` and `services/`. Changing `authDomain`
would have meant editing six files and getting all six right; one miss and
some pages authenticate against a different domain than others.

It is now a single module, `js/firebase-config.js`, which everything imports.
`authDomain` is derived from one boolean.

**No behavioural change was shipped.** The flag is `false`, so every page still
resolves `rabbihossainltd-63709.firebaseapp.com` exactly as before — verified in
a browser across six pages with zero console errors, and the real Google popup
still completes and shows the current text.

## 6. Note on the "App name"

Even after the domain switch, Google shows the *domain*, not "Rabbihossainltd",
for unverified apps. To get the brand name and logo on the consent screen the
app must go through **OAuth verification** in Google Cloud. With only
`openid` and `userinfo.email` requested (both non-sensitive), verification is
usually light-weight, and the domain must be verified first — which the
existing `google-site-verification` TXT record already satisfies.

Showing `rabbihossainltd.online` instead of `rabbihossainltd-63709.firebaseapp.com`
is the meaningful win here and needs no review.
